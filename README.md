# Shuvia · Phase 2

For the application architecture, request/data-flow diagrams, security boundaries, and change guide, see [docs/SYSTEM_DESIGN.md](docs/SYSTEM_DESIGN.md).

For the public website, registration and invitation-entry changes, plus implementation and verification status, see [docs/platform-implementation-report.md](docs/platform-implementation-report.md).

Shuvia now runs on Next.js App Router. Supabase Auth owns passwords and verified-email state; application data is protected by row-level policies. Password recovery links are generated by Supabase on the server and delivered through the Brevo transactional email API.

## Configure local development

1. Copy `.env.example` to `.env.local` and fill in the Supabase project URL, publishable/anon key, service-role key, Brevo API key, and a random `AUTH_FLOW_SECRET` (32+ characters). `BREVO_SENDER_EMAIL` is prefilled with the verified sender supplied for this project.
2. In Supabase, enable email confirmations and run the SQL in `supabase/migrations/202611250001_auth_and_onboarding.sql`.
3. Add `http://localhost:3000/auth/callback` and your production callback URL to Supabase Auth’s allowed redirect URLs. Set the Site URL to your deployed Shuvia origin.
4. Verify `subhamv2003@gmail.com` as a sender in Brevo and add its API key to `.env.local`. Keep service-role and Brevo keys server-only; never prefix them with `NEXT_PUBLIC_`.
5. Run `npm run dev`.

Supabase Auth’s built-in rate limits remain enabled for signup, login, and email verification. Recovery-email and onboarding writes use the database-backed rate-limit function in the migration. Review Supabase’s Auth, SMTP, password-policy, and site URL settings before production deployment.

The `/terms` and `/privacy` pages are explicitly launch placeholders, not legal advice or final policies. Replace them with reviewed Shuvia policies and increment `legal_version` in the signup form when they are approved.

## Couple connections

After the auth migration, also run `supabase/migrations/202611250002_private_couple_spaces.sql`. Couple mutations go through authenticated Postgres RPCs; the browser cannot read invitation rows or write room membership directly. The database locks each room during acceptance, limits each room to its owner and one partner, and allows each user one open connection at a time. A 256-bit link token is shown only once and stored as a SHA-256 hash. The 10-character code is also only shown at creation and stored as an HMAC using `AUTH_FLOW_SECRET`. Invitations expire after seven days; regenerating one cancels its predecessor.

Connection consent is staged: the owner consents while creating the invitation, the partner explicitly accepts, then the owner confirms. Either partner can disconnect after connection. The room policy is `delete_on_disconnect`: shared room content is removed in the same disconnect transaction, while individual accounts/profiles remain and minimal connection audit events are retained.

## Couple dashboard

After migrations 1 and 2, run `supabase/migrations/202611250003_couple_dashboard.sql`. The private home is `/home`; it requires a verified, onboarded user with an active connection. Notes, special dates, memories, and activity are written through narrow authenticated Postgres functions and protected by RLS. On disconnect, all of these shared records are deleted atomically.

Realtime Presence and Broadcast authorization is scoped to `couple:<space UUID>` and requires an active member of a connected space. Dashboard activity uses Postgres Changes for the member-scoped activity feed. The bottom navigation is designed for mobile and links to the same private features as desktop.

For a two-device check, connect two verified/onboarded accounts using the Phase 3 steps. Keep `/home` open on device A, then open `/home` on device B and confirm each sees the other's online state and the partner-joined notice. Add a love note, a future date, and a memory on device A; confirm each appears on B without a manual refresh. Open `/games` on both, start a prompt on A, and confirm it opens on B; send answers in both directions and confirm they disappear after leaving. Disconnect from either account and verify both are disconnected and the notes, dates, memories, and activity have been removed. These live checks require the Supabase migration to be applied and two real accounts; this repository does not contain project credentials or a local database runner.

## Interactive couple games

After migrations 1-3, run `supabase/migrations/202611250004_interactive_games.sql`. `/games` now contains eight curated card decks, six category choices (including a mixed deck), instructions, turn/answer modes, pause/resume, skip/next, completion, replay, and recent history. Game APIs authenticate from the server session, validate inputs against the curated bank, and call service-role-only Postgres transitions. Game tables have RLS enabled and no client table grants. A unique answer key prevents duplicate submissions; the server reveals independent and guess/answer responses only after both people submit. Turn-based truth/dare reveals after the assigned player submits. Games and answers are deleted when the shared space disconnects. Private Realtime broadcasts carry a change signal only; answer text stays in the authorized API response and database.

Two-account game check: with both accounts signed in on separate devices, run every deck (`Truth or Dare`, `Would You Rather`, `How Well Do You Know Me?`, `Guess My Answer`, `Complete the Sentence`, `This or That`, `Emoji Love Challenge`, `Deep Love Questions`). For each, choose a category, confirm both devices show the same prompt, submit independently where applicable, verify the first response remains hidden, and verify both appear after the reveal condition. Check turn changes, pause/resume on both devices, skip, next round, finish, replay, refresh/reconnect, and history. For truth/dare, verify the non-turn player cannot answer. For emoji cards, try more than five symbols. The repository has no Supabase project configuration, so this integration test must be run after applying migration 4 and creating two registered accounts.

For a live two-account check, create two distinct Supabase users, verify both emails, complete onboarding, create an invitation from account A, then open the link or enter its code while logged in as account B. Accept from B, confirm from A, verify both see the connected state, then disconnect from either account and verify both see the closed state. Also try accepting the same invitation from a third account and accepting a second room while connected; both should be rejected. This repository has no Supabase credentials or local database runner, so that live test still needs to be run after project setup.

## Love notes and surprises

After migrations 1-4, apply `supabase/migrations/202611250005_love_notes_surprises.sql`. `/notes` offers four paper styles, immediate or scheduled delivery (up to 30 days), recipient-only letter bodies, an envelope opening, read state, favorites, and sent/received history. Scheduled titles and bodies stay hidden from the recipient until the release time; senders see delivery metadata, not a copy of the letter. `/surprises` includes a once-daily couple-wide scratch reveal, a server-selected shared wheel result, compliments, virtual hugs and kisses, playful challenges, date ideas, and conversation prompts. Curated text is bundled locally; no paid AI or content API is used.

Letter bodies, notification rows, and surprise history are read through service-role-only database functions after the server confirms email verification, onboarding, and active membership. The browser cannot query or write these private tables directly. Couple Realtime broadcasts contain no message or result text; clients reload through the membership-checked APIs. Letters, notification state, and surprise history are deleted when the couple disconnects. Letter sends and surprise actions use the existing database-backed rate limiter.

For a two-account check, connect two verified/onboarded accounts on separate devices. Send an immediate letter from A and verify only B can open/read it; favorite it on B and verify it appears in B's kept-close tab. Schedule a letter from A and confirm B sees a locked envelope without title/body until its release time, then open it and confirm read state appears in A's sent tab. From either account scratch today's card and verify the same result appears on the other device and after refresh. Spin the wheel from A and confirm B sees the same category and result; test the remaining surprise actions, notifications, reconnect, rate limit, and disconnect cleanup. This live test still requires project credentials, migration 5 applied, and two actual accounts; those aren't present in this workspace.

## Memories and special days

After migrations 1-5, apply `supabase/migrations/202611250006_memories_and_special_days.sql`. `/memories` is a room-scoped photo scrapbook with timeline and masonry gallery views. New photos are resized and converted in the browser, signature-checked by the server, and saved to the private `shuvia-memories` Storage bucket. Photo records use couple-space paths; signed read links are issued only after membership checks and expire after one hour. Uploads are limited to 8 MB and JPEG, PNG, or WebP. Members can edit memory details/photo, or remove the memory and its photo.

`/our-days` stores the relationship start date, shows days together and an anniversary countdown, and supports birthdays (with the person attached), custom events, and recurring annual dates. Both pages reload through authorized server functions and send content-free Realtime updates to the other member. Couple disconnect cleanup removes associated photo objects after the shared records are closed; private bucket policies also deny the old room after disconnect.

Two-account test: upload a photo and add a title, description, and past date from account A; retrieve it on B and confirm the contributor name/photo render. Edit the text/date, replace and remove the photo, and confirm updates arrive on B. Delete the memory and verify the row and storage object are gone. Add a relationship start date, confirm days together and the anniversary countdown; add birthdays for both members and a recurring custom event, edit and delete entries, then refresh both devices. Try accessing a photo URL as an account from another room and confirm it is denied. Live storage and membership checks require migration 6 and configured Supabase credentials; this workspace has no `.env.local` or Supabase CLI.

## Account settings and application polish

Apply migrations 1-6, then run `supabase/migrations/202611250007_account_settings.sql`. `/settings` lets a verified user update their display name, private avatar, email (with Supabase confirmation), password, onboarding answers, theme, notification/audio preferences, privacy controls, and couple-space links. Email, password, and account deletion actions ask for the current password. Account deletion requires the typed phrase `DELETE MY ACCOUNT`, closes an active couple space, removes its shared database content and stored photos, revokes all sessions, then deletes only the signed-in user's Auth account. Avatars use a private per-user Storage path and one-hour signed display links.

The public policy and terms pages are launch drafts; review them for the jurisdictions where Shuvia operates. `/contact` currently uses the verified sender address configured in `.env.example`. The app includes a manifest and install prompt, offline fallback, network/reconnection status, global error boundary, branded not-found page, and social metadata. The service worker only caches the offline page and icons; it does not cache authenticated page responses.

Local checks: `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build`. To validate live account flows, configure `.env.local`, apply migration 7, then verify avatar upload/removal, email-change confirmation, password change, preferences on a second device, disconnect cleanup, and deletion using two separate registered accounts. This workspace has no Supabase project credentials or CLI, so provider email, storage, and two-account flows cannot be exercised here.
